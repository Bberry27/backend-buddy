# Risk register

Every risk named in the approved plan (RK-01 to RK-11), followed by risks confirmed during the code exploration that the plan addresses only implicitly (RK-12 onward). Likelihood and impact are qualitative (High / Medium / Low); no probabilities or cost figures are estimated. A trigger is the observable event that says the risk is materialising, so that a verifier can check it rather than guess.

Review cadence: the register is re-read at every gate (G0, G1, G2) and whenever a trigger fires. Closing a risk requires naming the test or control that now covers it. Owner is a role, never a person.

Snapshot note: Phase 0 documentation and the Phase 1 bootstrap packages R00 and R01 ran in parallel, so every "today" statement in this register was checked against a tree that changed while D04 was written. Rows marked "re-verified 2026-09-07" were checked again after R00 and R01 landed; the status header still reads `pre-repo` because the directory is not yet a git repository.

### Known open instances (section A)

- RK-01: `scripts/verify_host.mjs` carried the table-count and column-count literals of the original private example on 8 lines (`:249`, `:261`, `:269`, `:278`, `:292`, `:303`, `:327`, `:334`). The R00 fix round replaced them with values derived from the embedded snapshot (`report.schema`) and added `scripts/verify_host.test.mjs`, which fails if a count literal returns; S02 completes the parameterisation (`--schema` cross-check). The RK-01 trigger "a reviewer sees a count literal" therefore no longer fires on `main`. The guard's checks (forbidden paths, size cap, machine-local paths, QA outputs, local name denylist via `BB_DENYLIST_FILE`) do not detect numeric carriers; the fixture tests now read a local-only numeric denylist from `BB_FORBIDDEN_COUNTS` (resolving the first half of open question 4).
