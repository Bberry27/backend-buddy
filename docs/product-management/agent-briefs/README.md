# Agent briefs

A brief is the single document a coding agent (or a person working like one) reads before starting a work package. It fixes what to read, what to change, what not to touch, what is frozen, what "done" means, and how to prove it. One brief per build work package, at `docs/product-management/agent-briefs/WP-<id>.md` (`WP-S01.md`, `WP-C03.md`, `WP-W05.md`, ...). D08 writes one brief for every S, C, W, A, O, and Q work package in `docs/product-management/roadmap.md`; R00 and R01 are executed by the owner's own session and D-track packages use the Phase 0 workflow rather than briefs.

Briefs are read by agents that may run concurrently in separate worktrees. The `may-modify` and `must-not-touch` globs are therefore not advice: two agents editing the same file is a merge conflict at best and a silent regression at worst.

## Execution model

1. The orchestrator assigns one brief per agent per worktree. Branch name and PR scope follow `docs/product-management/traceability.md` section 2.
2. The agent follows the reading list in order, then works only inside the `may-modify` globs.
3. When the agent claims "done", a verifier agent runs the acceptance commands from the brief on a clean checkout of the branch and tries to refute the claim: it checks every definition-of-done item, every frozen contract, and diffs the changed paths against the globs.
4. A completeness critic at the end of each phase lists unmet acceptance criteria as the next round's work.
5. Anything the agent finds that is out of scope is written in the report's "Out of scope, found" list, not fixed.

## Brief format

Every brief has the twelve sections below, in this order, with these headings. The docs lint (Q05) checks the status header (DL-01) and the twelve-section heading order (DL-16, `docs/product-management/traceability.md` section 4) for `WP-*.md`.

### Header

```
Status: draft | Owner: <role> | Last verified against code: <commit or pre-repo (YYYY-MM-DD)>

# WP-<id> <title from roadmap.md>

| Field | Value |
|---|---|
| Work package | <id> (track <D/R/S/C/W/A/O/Q>, phase <0/1/2>) |
| Features | F## ... (ids from docs/features/README.md; "none" for pure infrastructure) |
| CTQs | CTQ-## ... (the ones this package must prove or must not regress) |
| Caveats | C## ... (the ones whose wording this package surfaces; quoted only from docs/reference/caveats.md) |
| Depends on | <WP ids that must be merged first> |
| Blocks | <WP ids waiting on this one> |
| Branch | <wp-id>/<slug> or f##/<slug> |
| Gate | G1 | G2 |
```

### 1. Goal

Two to four sentences: the outcome, in terms a verifier can check. Copied from the roadmap scope and sharpened; no new scope.

### 2. Reading list (ordered)

Numbered, in the order to read. Always: feature document(s) first, then the contract (`docs/architecture/schema-graph-contract.md`, `packages/contract/schema-graph.v1.json` once C01 lands), then the relevant ADRs, then the existing code with `path:line` pointers to the exact functions to reuse. Then the engineering standards that apply (`docs/engineering/standards.md`, `security-policy.md`, `testing-policy.md`, `accessibility-standards.md`). Each entry says what to take from it in one clause.

### 3. In scope

Bullet list of deliverables. Each maps to a roadmap scope item or a feature behaviour (`B#`). Nothing here that the acceptance commands cannot check.

### 4. Out of scope

Bullet list of adjacent things the agent must not do, with the id of the package or L-item that owns each. This is where scope creep (risk RK-10) is stopped.

### 5. May modify

Globs, one per line, of paths the agent may create or edit. Narrow by default: a package, a directory, named files. Example for a view package:

```
packages/explorer/src/City.tsx
packages/explorer/src/City.css
packages/explorer/src/city-layout.ts
packages/explorer/src/city-layout.test.ts
tests/e2e/city.spec.ts
docs/features/F08-schema-city.md        (sections 3 and 14 only)
CHANGELOG.md                            ([Unreleased] section, one line)
```

### 6. Must not touch

Globs the agent must not edit, even to fix something obvious. Always includes:

```
skill/assets/extensions/**              generated mirror; run npm run build instead
fixtures/**                             generated; change scripts/generate-fixtures.mjs only if in scope
THIRD_PARTY_NOTICES.md                  generated by scripts/generate_notices.mjs
package.json, package-lock.json         unless the brief lists a dependency change
packages/explorer/src/types.ts          unless the brief is C01 or C03
skill/assets/explorer.html              unless the brief is S01, S03 (live bridge only), or W03 (inline renderers only)
skill/scripts/build_explorer.py         unless the brief is S01
docs/reference/caveats.md               frozen at G0
.github/workflows/**                    unless the brief is R00, S02, O01 (compose-smoke job), O02, or Q05 (PR-title regex and docs-lint steps)
```

plus the package-specific list. A path in neither list is "ask first". The exceptions mirror the key-files column of the approved plan as carried in `roadmap.md`; a brief that needs a path outside its exception raises it through roadmap change control instead of editing this list.

### 7. Frozen contracts

The invariants this package must preserve, each with where it is defined and the test that pins it. Select from the repository-wide list below and add package-specific ones (a selector contract, a storage key, a CLI flag).

### 8. Deliverables checklist (definition of done)

The checklist below, with package-specific additions after it. It is aligned with the approved plan's definition of done; the canonical text lands in D03 (`docs/engineering/definition-of-done.md`), after which this section, `AGENTS.md` section 5, and `.github/PULL_REQUEST_TEMPLATE.md` reference that file instead of restating it (today the three restatements differ in wording and grouping). A brief may strike an item only by writing why it does not apply (for example "Migration: none, because this package has no server-side state").

- [ ] Code and tests, test names prefixed with the F/CTQ id, green locally with the acceptance commands
- [ ] Feature document sections 3 (current state) and 14 (implementation map and change log) updated
- [ ] Migration with a tested downgrade, or "none, because ..."
- [ ] `CHANGELOG.md` line under `[Unreleased]`, prefixed with the id
- [ ] Release-note line in the PR body
- [ ] Security checklist from `docs/engineering/security-policy.md` completed
- [ ] Accessibility result recorded (axe serious/critical = 0 and a keyboard journey where UI changed)
- [ ] Performance measurement recorded where a budget exists (CTQ-09, `docs/reference/limits-and-caps.md` B)
- [ ] Caveat text only from `packages/explorer/src/caveat-strings.ts`; until C03 lands, the temporary rule is a verbatim quote from `docs/reference/caveats.md` (the plan's DoD names `caveat-strings.ts` only)
- [ ] `npm run guard` green; no private schemas, screenshots, or QA reports added
- [ ] `npm run build` run and the mirror committed if `packages/explorer` changed
- [ ] All changed paths inside the `may-modify` globs

### 9. Acceptance commands

The exact commands the verifier runs, in order, from the repository root on ubuntu, with the expected result of each. Commands must be copy-pasteable; no placeholders except `<out>` for an output directory. Typical set:

```sh
npm run restore
npm run guard
npm run typecheck
npm test
npm run build
node scripts/verify_host.mjs dist/backend-buddy.html <out> --widths=1920,1366,390
npx playwright test tests/e2e/<feature>.spec.ts          # after S02
python -m unittest discover -s packages/explorer/server -p 'test_*.py'
node scripts/docs_lint.mjs                                # after Q05
```

Followed by the package-specific assertions ("`grep -c 'data-selected=\"true\"' ...` equals 1", "`report.json` has `externalRequests: []`").

### 10. Reporting format

The agent's final report, in this order, so the verifier and the orchestrator can parse it:

1. **Files changed**: repo-relative paths, each tagged `added | modified | deleted`, and a statement that all are inside the `may-modify` globs (or which are not and why).
2. **Acceptance commands run**: each command with its exit status and the relevant output line(s); "not run" with a reason where applicable.
3. **Definition of done**: the checklist with each item ticked, struck with a reason, or left open.
4. **Frozen contracts**: one line per contract, "preserved" with the test that proves it, or "changed" with the ADR or approval that permits it.
5. **Measurements**: any CTQ number produced (bundle size, TTI, frame median, coverage, axe counts).
6. **Out of scope, found**: issues noticed but not fixed, each with the WP or L-item that should own it.
7. **Open questions for the owner**: numbered, each with the decision needed and the gate by which it is needed.
8. **Deviations**: anything done differently from the brief, and why.

No prose summary beyond these sections. No screenshots of anything but synthetic fixtures.

### 11. Risks

Risk ids from `docs/product-management/risk-register.md` this package touches, and what the agent must do about each (usually: run a named test, keep a named control).

### 12. Change log

Rows appended when the brief itself changes (date, PR, what changed and why). A brief changes only through a PR.
