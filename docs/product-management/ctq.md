# Critical-to-quality registry (CTQ-01..16)

A CTQ is a quality requirement the product must meet before a gate opens. Each row names the metric, the target exactly as approved in the plan, the command or test that measures it, the role that owns the number, and the gate at which it is enforced. Feature documents (`docs/features/F##-*.md`) tag their acceptance criteria with these ids; `docs/product-management/traceability.md` maps features to CTQs; `docs/reference/limits-and-caps.md` section B is the single place the numeric budgets are recorded.

Rules:

1. Targets are changed only by a reviewed PR that updates this file, `limits-and-caps.md`, and the test that pins the value.
2. A measurement that has no automated command yet is marked with the work package that delivers it. Until that WP lands, the CTQ is measured by the interim method in the "Today" column and reported in the PR description.
3. Every PR records the measured value for each CTQ its feature document lists (definition of done in `docs/engineering/definition-of-done.md`). "Not measured" is a failing result, not a blank.
4. No target in this file is an estimate of what the code does today. Baselines are recorded in `docs/qa/perf-baselines.md` (Q01) once measured.

## Gates

| Gate | Meaning | Where the exit criteria live |
|---|---|---|
| PR | Enforced on every pull request by CI (`.github/workflows/ci.yml`, `.github/workflows/security.yml`) or the pre-commit hook (`.githooks/pre-commit`). | This file, column "Gate" |
| G0 | Documentation approved by the owner; caveat wording frozen. | `docs/product-management/roadmap.md`, section "Gate G0" |
| G1 | Bootstrap, hardening, and contract complete from a clean clone on ubuntu CI. | `roadmap.md`, section "Gate G1" |
| G2 | MVP complete; all automated CTQ checks green plus UX round 1. | `roadmap.md`, section "Gate G2" |
| REL | Re-verified for every tagged release (`release.yml`, O02) in addition to the PR checks. | `docs/qa/release-checklist.md` (Q04) |

A CTQ tagged "G1, then PR" is first proven at G1 and then runs on every PR.

## Notes per CTQ

- **CTQ-01**: the plan requires distinguishability in the DOM, not only in copy. Views that encode counts (F05, F06, F07, F08, F09, F11, F13) must set `data-rowcount` on the element that encodes the value. Canonical wording is caveat C01 in `docs/reference/caveats.md`; UI strings come from `caveat-strings.ts` after C03.
- **CTQ-02**: the artifact and SPA matrices share the same widths so `docs/qa/perf-baselines.md` and screenshots are comparable. Breakpoints in the host today are 1800/1050/700 px (`explorer.html` CSS); the matrix widths are chosen to straddle them.
- **CTQ-05**: the byte-identical requirement is decision D9. The only permitted deviation is the live-mode copy served by `serve_explorer.py`, which rewrites `connect-src 'none'` to `connect-src 'self'` (`packages/explorer/server/serve_explorer.py:68`); that copy is out of scope for this CTQ and in scope for CTQ-07.
- **CTQ-06**: the rule "a drill-through may prefill a live query but never runs it without a click" belongs to F14 and is measured here because its failure mode is executing a query.
- **CTQ-08**: `DEADLINE_SECONDS` is a whole-operation deadline today (`schema_profiler.py:78`); the MVP replaces it with per-table budgets (default 5 s, max 60 s) and a job cap (default 600 s, hard max 3600 s). Both sets of values are recorded in `limits-and-caps.md`. Module-level constants stay patchable because `test_schema_profiler.py:201-213` patches them.
- **CTQ-09**: no baseline exists. Q01 records the first measurement in `docs/qa/perf-baselines.md`; budgets are enforced as warnings until two green weeks (risk register RK-07), then as failures.
- **CTQ-10**: the remount count is observable only after W01 exposes `window.__backend-buddyMounts` in non-production builds; the artifact equivalent is the `verify_host.mjs` remount counter added in S02.
- **CTQ-11**: axe runs are per route, theme, and width; a single violation of severity serious or critical fails the gate. Moderate and minor violations are recorded in the PR and triaged by the Design and accessibility lead.
- **CTQ-12**: thresholds are per package. "Logic" means the pure modules in `packages/explorer/src/*-logic.ts`, `city-layout.ts`, `route-state.ts`, `selection.ts`, `navigation.ts`; "components" means `.tsx` files; "auth/crypto/policy" means `services/api/app/{auth,crypto}/**` and `packages/profiler/bb_profiler/policy.py`.
- **CTQ-13**: until `docs_lint.mjs` exists (Q05), the adversarial review at G0 and the PR review perform the checks by hand using the rule list in `traceability.md`.
- **CTQ-14**: the guard's name denylist is deliberately local so the private name never appears in the repository, including inside the rule that would detect it.
- **CTQ-15**: "clean machine" means a fresh ubuntu CI runner with Docker only; no cached images or volumes.
- **CTQ-16**: audit rows are insert-only by a database trigger (A01); the application never holds a role that can bypass it.
