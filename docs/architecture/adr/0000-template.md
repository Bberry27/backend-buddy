# ADR-NNNN: <short noun phrase>

- **ADR status**: proposed | accepted | superseded by ADR-XXXX | deprecated
- **Date**: YYYY-MM-DD
- **Deciders**: roles, not names (for example Product owner, Frontend lead, Security lead)
- **Work packages**: the WP ids that implement this decision
- **Related**: other ADRs, feature documents (F##), contracts

## Context

What is true today, with verified `path:line` citations against the commit in the status header. State the forces: constraints, existing code that must keep working, caveats (quote by C-id from `docs/reference/caveats.md`, never paraphrase), and the problem a decision must solve. Do not include private example data or its name; write "the original private example" if a reference is unavoidable.

## Decision

The decision in one paragraph, then the specifics as a numbered list. Name the modules, files, contracts, and defaults it fixes.

## Consequences

- Positive: what becomes possible or simpler.
- Negative: what becomes harder, slower, or more costly, and how it is mitigated.
- Neutral: things that change without being better or worse.

## Alternatives considered

One bullet per alternative: what it is, why it was not chosen. Include "do nothing".

## CTQs affected

CTQ ids from `docs/product-management/ctq.md` with one line each on how this decision moves the metric.

## Verification

The tests, scripts, or CI jobs that prove the decision is implemented as written (names, not descriptions), and the gate (G0/G1/G2) at which they are required.
